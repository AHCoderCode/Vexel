Debug JavaScript step by step

When a website feature does not work, rewriting the whole project is rarely the best first move. A repeatable debugging process helps you identify the exact failure, understand its cause, and test the smallest change that should fix it.

A practical guide · About 8 minutes

JavaScript bugs can appear as a blank page, a button that does nothing, an incorrect result, or an error that appears only after a certain action. The most useful starting point is a specific, repeatable description of the failure rather than a guess about the cause.

1. Reproduce the problem reliably

Write down what you expected, what actually happened, and the steps needed to see it. For example: “On the signup page, when both password fields contain the same six-character value and I click Create account, no message appears.” This is much more useful than “signup is broken.”

Try the shortest sequence that produces the problem. Note whether it occurs every time, only for one input, or only after reloading the page. Do not change several unrelated things before you have recorded the original behaviour.

2. Read the browser console

In Chrome or Edge on Windows, open the page, press F12, and choose the Console tab. You can also right-click the page, choose Inspect, and open Console. Reload the page to see startup errors, then repeat the action that triggers the bug.

  • SyntaxError: the JavaScript text cannot be parsed, often because of a missing bracket, quote, or comma.
  • ReferenceError: code refers to a name that is not available where it is used, such as a misspelled variable.
  • TypeError: an operation is being used with a value that does not support it; for example, calling a method on null.
  • Network or API error: a request may have failed, credentials may be misconfigured, or a remote service may have returned an error.

Click the file-and-line link beside an error to inspect the relevant code. The first error can cause several later errors, so start at the earliest relevant failure instead of fixing each downstream message blindly.

3. Isolate the smallest relevant section

Find the button, form, function, or request involved. Check that the HTML element has the ID the script expects, that the script loads, and that the event listener is attached after the element exists. For example, this listener will fail if there is no element with the matching ID at the moment the code runs:

const button = document.getElementById("saveButton");

button.addEventListener("click", () => {
  console.log("Save button was clicked");
});

If the HTML actually uses id="saveBtn", then getElementById("saveButton") returns null. Confirm the actual ID before adding more code. A basic check can make the failure easier to spot:

const button = document.getElementById("saveButton");

if (!button) {
  console.error("The save button was not found in the HTML.");
} else {
  button.addEventListener("click", () => {
    console.log("Save button was clicked");
  });
}

This is an illustration, not a universal patch: the correct ID and placement depend on your page. First check the actual DOM and script loading order.

4. Trace values instead of guessing

Use focused logs around the point where you suspect the value changes:

console.log("Form submit started");
console.log("Username is present:", Boolean(username));
console.log("Validation passed:", isValid);

Prefer logging whether sensitive values are present instead of printing passwords, session tokens, personal information, or private chat contents. Remove temporary logs after diagnosing the issue if they are no longer needed.

For more complicated code, use breakpoints in the Sources tab. A breakpoint pauses execution so you can inspect the current line and the variables available at that point. Step through a few lines to see exactly where behaviour differs from what you expected.

5. Test one focused change

  1. State the likely cause and the evidence supporting it.
  2. Change only the code needed to address that cause.
  3. Repeat the original steps and confirm the expected outcome.
  4. Test a nearby edge case, such as an empty field or an invalid value.
  5. Check the console again for new errors.

If the fix does not work, revert that change or reconsider the hypothesis. Stacking guesses on top of guesses makes it harder to know what changed the result.

6. Give an AI assistant enough evidence

When asking AI for help, share a minimal reproducible example: the exact error, the relevant HTML, the event handler or function, and the browser or runtime. Explain what you expected and what happened. Ask for the smallest patch first and request an explanation of why the error occurs.

Example debugging request

Environment: Chrome on Windows, plain HTML/CSS/JavaScript.
Expected: clicking Save shows a success message.
Actual: nothing happens.
Console: [paste the exact relevant error]
Relevant HTML: [small snippet]
Relevant JavaScript: [event listener/function]

Please identify the earliest likely failure, explain it simply,
and propose the smallest fix. Do not rewrite unrelated files.
Give me one or two tests that can confirm the fix.

Review the suggested change before using it. AI can invent APIs, overlook how your files connect, or confidently diagnose the wrong line. Verify the patch in your own project and keep a working copy or version-control commit so you can undo a bad change.

Protect your project while debugging

  • Never paste secret API keys, service-role keys, passwords, or authentication tokens into a public issue or chat.
  • Share the smallest snippet needed; remove real names, account details, and private data.
  • Keep server-only credentials in environment variables and server-side code, not browser JavaScript.
  • Do not disable security checks just to make an error disappear; understand the cause and use a safe fix.

A dependable rule

Reproduce the bug, inspect evidence, isolate the smallest cause, make one change, and verify the result. This approach is slower than guessing for a minute, but usually faster than repeatedly rewriting code that was already working.
